# 6\.2b 层0先验记忆深入：谁主导模型行为

> 本节深入 6\.1b 框架的“层0先验记忆”。6\.1b 建框架时标了层0的待验证点（先验和经验谁优先、边界在哪、怎么协同），本节用三家源码实证回答，并提炼对 harness 设计的核心启发。
> 层0四类先验中，模型权重（训练知识）和 skills \(8\.6b 已述\) 不在本节范围。本节聚焦 **CLAUD/AGENTS\.md（项目先验）** 和 **四类先验怎么协同注入**。
>
>

## 6\.2b\.1 源码事实：三层层0先验机制

### CLAUDE/AGENTS\.md 的加载—层级化项目知识

**CC 四层作用域（****`claudeend.ts:4-16`****，最精细）：**

|层|文件|作用域|人的类比|
|---|---|---|---|
|Managed|`/etc/claude-code/CLAUDE.md`|全局所有用户（管理员设）|公司规章|
|User|`~/.claude/CLAUDE.md`|用户私有全局（所有项目）|个人工作习惯|
|Project|`CLAUDE.md` / `.claude/CLAUDE.md` / `.claude/rules/*.md`|项目级（checked into 代码库）|项目规范|
|Local|`CLAUDE.local.md`|项目私有（不提交）|个人项目笔记|

加载方式：`"traversing from the current directory up to root"`—从当前目录**向上遍历到根**，收集路径上所有 CLAUDE\.md。层级化、可叠加。

**Codex 路径拼接（****`agents_md.rs`****，中等）：** 从项目根（`.git` 标记）**向下到当前目录**，收集路径上所有 AGENTS\.md 并按顺序拼接。注释原文：`"Collect every AGENTS.md found from the project root down to the current working directory and concatenate their contents in that order."`

**dsh baseline reactive（****`agent-instructions/index.ts`****，最动态）：**`"Baseline instructions enter durable context before the first request; successful fs tool touches project nested, changed, and removed instructions into the inbox."`—baseline 进 Cordis durable context，**文件变化→inbox 更新→context 自动反映**。

### 注入位置—三种范式

||CC|Codex|dsh|
|---|---|---|---|
|CLAUDE\.md/AGENTS 注入|prependUserContext → 「\<user消息\> \+ \<project\-instructions\>标签」|base\_instructions → **system消息**（instructions）|durable context baseline → **Cordis context**|
|优先级|user 级（但 project\-instructions 高权重）|system 级（和 SystemPrompt 同级）|context 统一管理|

### 经验记忆的注入位置—关键发现（含旧版勘误）

> 旧版勘误：本节旧版声称“经验记忆（MEMORY\.md）通过 LoadMemoryPrompt 送 system 段，所以经验 \> 先验”。经源码逐条核验，**这个结论建立在混淆之上，是错的，修正如下。**
>
>

CC 的记忆**分两路注入，不能混为一谈：**

1. **记忆机制说明 prompt** — `LoadMemoryPrompt()` 进 **system 段**`memory section`（`prompts.ts:458 systemPromptSection('memory', () => loadMemoryPrompt())`）。但 `LoadMemoryPrompt()` 返回的是 `buildMemoryLines(...).join('\n')`（`memdir.ts:475`），内容是**auto memory 目录路径 \+ 教模型怎么记忆系统的指南**——**不是记忆条目本身**。它在 system 段，但只是操作说明，不含任何具体经验。

2. **记忆条目内容** — `relevant_memories` attachment 进 **user 消息**（`messages.ts:4119` 的 `case 'relevant_memories'`，经 `wrapMessagesInSystemReminder(createUserMessage(...))`）。`getRelevantMemoryAttachments`（`attachments.ts:2258`）调 `findRelevantMemories` 按本轮输入相关性排序 → top5 召回 → 每条 `memoryHeader` → 经 `system-reminder` 包成 user 消息。**这才是“用户偏好”“支付超时护罩”等真实经验条目的去向。**

而 CLAUDE\.md — `prependUserContext`（`api.ts:443`）进 **user 消息**，但用 `project-instructions` 标签（`api.ts:464`），**不是 system\-reminder**。源码注释原文（`api.ts:457-459`）：

> `"Extract claude as a dedicated high-weight user message so it isn't buried inside the generic "system-reminder" with the 'may or may not be relevant' disclaimer, which would degrade its instructional weight"`
> —CC 故意把 CLAUDE\.md 独立成比普通 system\-reminder 更高权重的标签。
>
>

所以 CC 的实际优先级真相：

- `system` 段（人格 \+ 记忆机制说明）— 最高，但**记忆机制说明不含条目**

- `project-instructions`（CLAUDE\.md 先验）— **高权重 user 消息**，CC 故意抬高

- `system-reminder`（记忆条目 \+ skills \+ 其他 context）— 带 `"may or may not be relevant"` 免责声明，权重**低于**`project-instructions`

> 记忆条目和 CLAUDE\.md 都在 user 消息里，但 CLAUDE\.md 走高权重的 `project-instructions`，记忆条目带走免责声明的 `system-reminder`。从注入位置看，CC 没有硬性 if\-else 优先级规则，最终谁主导模型语义判断（6\.2b\.4）。
>
>

## 6\.2b\.2 核心事实：注入位置 = 标签权重杠杆（非经验/先验优先级）

把层0四类先验 \+ 经验记忆的注入位置合看（按修正后的源码真相）：

> 图 6\-3：CC 的先验/经验注入位置（红=SystemPrompt人格最高；黄=记忆机制说明进system段但不含条目；蓝=CLAUDE\.md走高权重project\-instructions；橙=记忆条目走system\-reminder；绿=skills走system\-reminder）
>
>

**核心事实（修正后）：**

- `system` 段最高的是**人格**；记忆机制说明也在 `system` 段，但只是操作指南不含经验

- **记忆条目（层1/2）和 CLAUDE\.md（层0 先验）都在 user 消息**—但 CLAUDE\.md 走 `project-instructions` 高权重标签，记忆条目走免责声明的 `system-reminder`

- 从标签权重看，**先验（CLAUDE\.md）\> 经验条目**—但这不是硬性优先级，最终靠模型语义判断

- **注入位置是“标签权重杠杆”，不是“经验/先验谁优先”的硬证据**。旧版把它当成“经验\>先验”的硬证据，是混淆了“机制说明进system段”和“条目进user段”。

## 6\.2b\.3 三家先验/经验优先级对比

||CC|Codex|dsh|
|---|---|---|---|
|SystemPrompt（人格）|system消息|system消息（instructions）|context persona（order\-0）|
|项目先验（CLAUDE\.md/AGENTS\.md）|user消息→project\-instructions标签（高权重）|system消息（base\_instructions）|context baseline|
|经验记忆（MEMORY\.md）|user消息→system\-reminder（带免责声明）|memory tool（模型主动调）|不独立（投影）|
|记忆机制说明（非条目）|system消息memory段|—|—|
|标签权重|project\-instructions \> 经验条目（system\-reminder）|先验（system）\> 经验（tool）|context统一|
|最终谁主导|靠模型语义判断（无硬规则）|先验主导（位置硬定）|靠 context 统一呈现|
|设计哲学|标签分层 \+ 模型判断|信任人设|统一管理不分优先|

**分野本质（修正后）：**

- CC 不用位置硬定谁优先 → **先验走高权重 project\-instructions，经验条目走低权重 system\-reminder，但谁主导靠模型语义判断（6\.2b\.4）**。CC 给的是“标签分层 \+ 模型裁决”，不是“经验\<先验”的硬声明。

- Codex 用位置硬定优先 → 先验进 system（高），经验是 tool（模型主动才看到）→ **先验 \> 经验，位置即优先级**

- dsh 不分优先 → 靠 Cordis context 管理协同，不显式排优先级

## 6\.2b\.4 核心启发：注入位置是“标签权重分层”的设计声明

从源码事实提炼的核心启发（修正后）：

> **所有先验/经验的注入位置 \+ 标签，本质是给模型排好权重梯度，让模型自己裁决的设计声明。**
>
>

CC 不用位置硬定谁优先，而是分三层标签权重：

1. `system` 段（人格 \+ 机制说明）— 最高 \+ cache

2. `project-instructions`（CLAUDE\.md 先验）— 高权重 user 消息，CC 故意从 `system-reminder` 里独立出来抬高

3. `system-reminder`（记忆条目 \+ skills）— 带 `"may or may not be relevant"` 免责声明，权重最低

这是**标签分层 \+ 模型语义裁决**范式—CC 给模型一个权重梯度，让模型在具体场景里自己判断“这条记忆条目 vs 这条项目规范，谁该主导”。而非 Codex 那样用 `system/user` 位置硬定优先级。

> 这对 harness 设计的启发（修正后）：设计记忆系统时，第一个决策不是“经验记忆该主导还是辅助”（CC 根本没设定），而是**“用位置硬定优先级（Codex式）还是用标签分层\+模型裁决（CC式）”** —这决定注入位置策略，进而反向决定记忆系统的设计重心。
>
> - 若 `标签分层 + 模型裁决`（CC 式）：记忆条目自低权重 `system-reminder`，靠模型按场景调用—记忆质量影响“是否被采纳”而非“是否注入”。提取/召回质量仍是重点（垃圾记忆进了也低权重，但好记忆要能被召回）。CC 不分配硬优先级，垃圾记忆只是被模型漠视。
>
> - 若 `位置硬定优先级`（Codex 式）：先验进 system 高位，经验是 tool 按需调用—记忆系统可轻量，因为先验主导。
>
>

## 6\.2b\.5 其他设计启发

**启发2：cache 稳定性张力** — `loadMemoryPrompt` 的机制说明在 `system` 段（`systemPromptSection('memory')`），但它**计算一次缓存到 /clear 或 /compact**（`systemPromptSections.ts` 的 memoize 语义）。不能每一轮都刷新 system cache。真正每轮可能变的是记忆**条目**（`relevant_memories` 按输入召回，top5 每轮不同），但条目在 user 消息、不碰 system cache。CC 把易变内容放 user 消息、稳定内容放 system，是**敏感的 cache 友好分层**。`DANGEROUS_uncachedSystemPromptSection`（`mcp_instructions`）才是真正每轮重算破坏 cache 的例外。

**启发3：冲突靠模型语义判断** — CC 没有显式“先验和经验冲突谁优先”规则，靠①标签权重分层（`system > project-instructions > system-reminder`）②模型自己理解。这是非确定手段（不写 if\-else 优先级规则），和 CC 整体范式一致（声明失效/skill 遵循都靠模型理解）。灵活但偶尔判错。

**启发4：作用域按“谁写\+谁可见”分** — CC 四层（Managed/User/Project/Local）不是按内容类型分，是按“谁写的\+谁能看\+该不该 checked in”分。比“内容类型”更本质—同一类内容（项目规范），团队写的（Project）和个人写的（Local）性质不同。

**启发5：先验可 reactive** — dsh 的 baseline 是 reactive 的（文件变化→inbox 更新），CC/Codex 是静态加载。reactive 更灵活（开发中改 CLAUDE\.md 不用重启），但要处理旧指令失效。Cordis 范式天然支持 reactive。

## 6\.2b\.6 案例：先验/经验冲突的实际场景

> **场景：用户在项目里工作，项目 CLAUDE\.md 写了“回答要简洁”，但 agent 从历史对话提取了记忆“这个用户偏好详细回答”。**
>
>

### CC 的处理（标签分层 \+ 模型裁决，非“经验\>先验”）

```
[system消息]
SystemPrompt: "你是自主agent..."（人格）
memory section: 记忆机制说明 prompt（教怎么用memory，不含“用户偏好详细”条目） → system段

[user消息]
<project-instructions> CLAUDE.md: "回答要简洁"（先验，层0） → 高权重标签
<system-reminder> relevant_memories: "Memory: 用户偏好详细回答"（经验条目，层1） → 带免责声明，低权重
```

模型看到：先走高权重 `project-instructions`，经验条目走低权重 `system-reminder` → **标签权重上先验 \> 经验，但模型按场景语义裁决**：可能理解“项目要简洁但这个用户偏好详细，按用户偏好来”或“项目规范优先，简洁为主”。CC 不硬定谁赢，给权重梯度让模型判断。

### Codex 的处理（先验 \> 经验，位置硬定）

```
[system消息]
instructions: "...你是agent..." + AGENTS.md "回答要简洁"（先验，base_instructions） → system段，高优先

[memory tool]
模型主动调 memory tool 查记忆（"用户偏好详细"） → tool，按需，低优先
```

模型看到：system 说“简洁”（先验主导），记忆要主动调才看到 → **先验优先，经验是补充**。

### dsh 的处理（统一 context）

```
[Cordis context]
persona: "..."（人格）
baseline: AGENTS.md "回答要简洁"（先验）
session-reference: 历史会话引用（含“用户偏好详细”的痕迹）
```

模型看到：context 里先验和历史引用都有 → **无显式优先级，靠 context 统一呈现，模型自己判断**。

### 三种处理的结果差异（修正后）

- CC：模型按场景裁决（先验标签权重高，但经验条目可被模型采纳）→ **非稳定，倾向取决于具体冲突语义**

- Codex：倾向简洁（先验主导）→ 合规但不够个性化

- dsh：模型自己判断 → 灵活但非稳定

> **这个案例的核心启示（修正后）：** “谁主导”不是 CC 用注入位置硬定的，而是设计哲学的分野—CC 用 **标签分层 \+ 模型裁决**（给权重梯度、模型按场景判断），Codex 用 **位置硬定**（先验进 system 就主导），dsh 用 **context 统一呈现**。设计 harness 时要 conscious 这个选择：**你要的是“灵活但非确定”（CC/dsh）还是“稳定可控”（Codex）**。
>
>

## 6\.2b\.7 记忆分层·作用域·晋升：三问收口（源码复核）

### 6\.2b\.7a 第一问：分层—“工作/短期/长期”三分法对吗？不对，三家用于三条不同的轴

> 认知心理学三分法映射到 agent 会卡在“短期记忆”：人类的短期记忆是**没转入长期就遗忘**的生理缓冲；agent 的“遗忘”不是生理衰减，是**显式工程动作（compaction/淘汰）**—三家都没有“会过期的中间层”。
>
>

||CC|Codex|dsh|
|---|---|---|---|
|会话历史 vs 跨会话记忆|transcript / memdir，两层，无过渡态|rollout\(DB\) / memories\(文件\)，两层|账本 / 投影，**不分层**|
|实际的分层轴|可推导性（grep 能恢复的不存）|加工深度（两阶段管记忆）|信任边界外（账本 vs 投影）|

> CC 的轴\-可推导性（`memoryTypes.ts` 注释原话）：`"记忆被约束为四种类型，用于捕获无法从当前项目状态推导出的上下文、代码模式、架构、git 历史、文件结构等可推导的——不应保存为记忆。"` —agent 用 grep/git 这个没有的“完美海马体”，人的“长期记忆”在 agent 处贬值成**可推导信号**。**分层的判断标准不是时间长短，是“这个信息还能从别处恢复吗”**。
>
> - Codex：Phase1（rollout\-DB 的 stage\-1 原料）→ Phase2（全局整合\+文件工件成品），像 episodic/semantic 的巩固流程，分层在**加工状态**而非时长。
>
> - dsh：的信任边界：账本是唯一本体，对话是投影，跨会话 `session-reference` 引用（按 URI 引用账本，不存独立记忆）。**唯一的层是账本 vs 投影**。
>
>

> 修正后的结论：分层是对的，即 6\.1b 已立的层0/1/2（按来源：人写先验/提取经验/反思认知）之外，**处置决策块三个正交轴**—\(a\)还能推导吗（决定存不存）\(b\)加工到什么深度（决定形态）\(c\)信任多少（决定怎么注入）。
> 别问“这条记忆算短期还是长期”，问三个问题—grep 能恢复它吗（能=不存）；它是原料还是成品（原料→过管道）；它值得多少信任（低→引用式送入）。
>
>

### 6\.2b\.7b 第二问：作用域—项目级？用户级？全局级？CC 用双体系给了全部答案

> 作用域不是目录硬切，是条目级软标签，由提取时的 LLM 按语义判断—与 6\.2b\.2 的“标签分层\+模型裁决”同构。**硬层（git 根目录）保安全，软层（scope 标签）保灵活**—又是“确定性防线\+语义裁决”配方。
>
>

**体系一：主线程 auto\-memory（memdir）—只有项目级，且刻意如此（****`paths.ts`****）**

```text
~/.claude/ (memoryBase)
└── projects/<sanitized-git-root>/memory/  → 项目键=git 根，不是 cwd!
    ├── MEMORY.md（索引，200行/25KB 上限）
    ├── 条目文件（user/feedback/project/reference 四类型）
    ├── team/
    └── logs/YYYY/MM/DD.md
```

两个精细点：

- **项目键用 ****`findCanonicalGitRoot`**（注释带 \#24382：所有 worktree 共享一个记忆目录—记忆代码实体定，不跟窗口视图走）；

- **目录覆盖是攻击面**—`autoMemoryDirectory` 设置被**前置校验 ****`projectSettings.ts`****（repo 里的 ****`.claude/settings.json`****）**。注释原话：`"a malicious repo could otherwise set autoMemoryDirectory: ~/.ssh/ and gain silent write access"`—不可信来源不许改记忆的物理边界。

**体系二：子代理 memory（****`agentMemory.ts`****）—完整三级，带枚举**

```ts
type AgentMemoryScope = 'user' | 'project' | 'local'
// user: ~/.claude/agent-memory/<agentType>/ → 全局！跨项目共享
// project: <cwd>/.claude/agent-memory/<type>/ → 进 repo，可 checked in
// local: <cwd>/.claude/agent-memory-local/<type>/ → 项目私有，不进 VCS
```

> 主线程和子代理走了两套相反的作用域策略—设计意图：主线程的个人经验绑定项目（“用户偏好简洁”在不同项目语境含义不同，全局会串味）；代理的技能性记忆（怎么读代码）跨项目稳定，才配 user 级。**分界判据：信息是否“语境无关”**。
>
>

**条目级还有第三层：scope 软标签**—`memoryTypes.ts` 的 COMBINED 段—**每条记忆带 private\|team 声明，四种类型默认 scope 各不相同且附判词：**

|类型|默认 scope|判词（源码原文级）|
|---|---|---|
|user|始终 private|用户偏好不污染团队|
|feedback|默认 private|`"仅当明确是每位贡献者都应遵循的项目约定（测试策略/构建不变量）而非个人风格偏好时才 team"`|
|project|强烈偏向 team|项目事实天然共享|
|reference|通常为 team|外部指针共享无害|

> 作用域标签不是目录硬切，是条目后打标签，由提取时的 LLM 语义判断—与 6\.2b\.2 的“标签分层\+模型裁决”同构。硬层（git 根目录）保安全，软层（scope 标签）保灵活—又是“确定性防线\+语义裁决”配方。
>
>

### 6\.2b\.7e 给设计 Harness 的启发（决策顺序）

**五条决策启发（按做设计时的决策先后）：**
